# The Separation Method — How to Think About It

This is a *way of thinking*, not a technical procedure. It is the practical form of the Separation Law.

## The question that starts everything

> How do we make a new tool by separating performance from the pattern that the performance follows repeatedly?

Every separation begins with this question. When a performance keeps following a pattern, the pattern is not the performance — the **pattern is a hidden tool** wearing the performance's clothes.

## The method in four moves

**1. Find the repeated pattern.**
Look at what performers keep doing over and over, across actors, across domains. The recurrence is the signal. (Auth, payment, cataloging, user management, backup, notification…)

**2. Separate the pattern from the performance.**
Remove the pattern from the individual performances. The performances should still be doable — they just become *composed* of tools rather than carrying the tools inside them.

**3. Let the pattern become its own layer.**
The extracted pattern is now a thing in its own right. As its own layer, it can be attached or detached on demand; it can be opened to everyone.

**4. Keep the performance as the money gate.**
What remains after separation — the actual act of creating value — is the performance. This is what gets monetized, and the people earning from it are the ones with the natural interest to keep the tool layer improving.

## The diagnostic law, used as a compass

When unsure whether something is a tool or the performance:

- **Delete it** → performance degrades?
- **Add it** → performance evolves?

Both true → it's a tool, separate and open it.
It *is* the value act → it's the performance, keep it gated.

## Attach / detach as the core operation

The insight that makes separation safe:

> Different concerns can be attached or detached from the last tool layer on demand.

- A performer who benefits from a concern **attaches** the open tool (self-serve).
- A performer who doesn't need it **detaches** it (stays lean).
- Nobody is harmed; everyone composes freely; the tool layer stays shared and open.

## The principle of "no lost performance"

When we decrease the tool, the performance degrades. When we add it, the performance evolves. This is not a warning against separation — it's the *measure* that proves a hidden tool exists, and the guide for how to re-compose so nothing is lost: detach the tool cleanly, and the performance can re-attach it from the open layer the moment it needs it.

## What this method produces

Every application of the method produces:

1. **A new open layer** (the extracted pattern, shared).
2. **A leaner performance** (the value act, now composable).
3. **A new stakeholder group** (everyone who was repeating the pattern before — now lifting each other).

Layer by layer, the same move repeats: find the pattern, separate it, open it, keep the performance gated.

## The open question the method keeps pointing at

The genuinely hard case, which you yourself named:

> There is a lot of performance that depends on tools **integrated into** the performance.

When a tool is fused into the performance, removing it damages the performance — so how do we separate it?

The beginnings of the answer, from the same law:

- If removing it *always and everywhere* degrades the performance, then it is not a standalone tool; it is part of that performance.
- If the *same* integration repeats across many performances, then the **integration itself is the repeated pattern** — and *that* is the thing to extract and open: a layer that does the integrating.

In other words, when you cannot pull the tool out, pull the *integration pattern* out instead, and make *that* the open layer.
